# ZenTimings CLI (Linux)

Saved BIOS settings plus opt-in experimental running UMC timings. Compiles the existing C# BIOS catalog/resolvers and embeds the same resources as WPF; no forked BIOS offset tables. Running mode compiles only the two pinned ZenStates-Core timing dictionaries, not its Windows hardware stack or PawnIO. The Windows project continues to target .NET Framework.

## Build

Requires .NET 10 SDK. From the repository root (initialize the pinned submodule first):

    git submodule update --init ZenStates-Core

    dotnet build cli/ZenTimings.Cli/ZenTimings.Cli.csproj -c Release
    dotnet publish cli/ZenTimings.Cli/ZenTimings.Cli.csproj -c Release -r linux-x64 --self-contained true -p:PublishSingleFile=true -o publish/linux-x64

The Linux CI artifact is a tar.gz containing a self-contained x64 executable (glibc Linux, no installed .NET runtime required; normal system libraries still required). Extract the archive into a dedicated directory. For origins/replay no driver loading is needed; for running timings an already installed and loaded ryzen_smu is required.

## Use

    ./zentimings --help
    sudo ./zentimings --origins
    sudo ./zentimings --json
    ./zentimings --replay report.txt --json

Use sudo only if needed for firmware read permissions. The CLI reads DMI identity in /sys/class/dmi/id and EFI variables in /sys/firmware/efi/efivars. It strips the four-byte little-endian attributes prefix before passing payload bytes to the shared resolver. It never writes firmware, clears immutable flags, loads drivers, mounts filesystems, or probes arbitrary variable names. Unknown boards/releases and mismatched fingerprints fail closed. An optional variable that is absent may be skipped, but an I/O error or malformed attribute prefix is not silently treated as absence. EFI runtime services can hide variables regardless of root permissions.

Live matching uses the shared Lenovo system family/machine type fallback, not BIOS version alone. All existing catalog evidence tiers still apply. A matched result means saved settings passed existing catalog/resolver checks; no claim that the hardware applied them. The default origins/replay modes remain unchanged and never access SMN.

### Capture for research (explicit opt-in)

Raw reports may contain private firmware data. Save locally with restrictive permissions and inspect before sharing; do not post full NVRAM on a public issue.

    (umask 077; sudo ./zentimings --debug > report.txt)

This attempts the five known variable names independently, with attributes, length, SHA-256 and payload base64. Capture does not require catalog recognition. No upload occurs. The ordinary table/JSON never contains raw blobs. The report uses the existing Windows resolver identity and variable base64 line format for offline replay. Windows debug reports containing those identity lines can be replayed on Linux; older reports may require explicit paired overrides:

    ./zentimings --replay report.txt --board 'ThinkCentre M75n' --bios M33KT24A --json

Offline replay never reads the current host's firmware. Exit codes: 0 matched (or debug captured at least one variable), 1 unavailable/unmatched, 2 invalid command or uncaught I/O error. For tests only, --sysfs-root points at a synthetic sysfs tree; never use arbitrary untrusted paths with sudo.

## Experimental running memory timings

    sudo ./zentimings --timings
    sudo ./zentimings --timings --json
    sudo ./zentimings --compare --json

Explicit opt-in only. Stop other users of the ryzen_smu SMN interface (including monitoring apps that use SMN) first. Do not run concurrently with firmware tuning software. The CLI does not install/load the driver, issue mailbox commands, write any register values, access PCI config directly or use /dev/mem. It uses the driver's four-byte address-only read request and reads back the four-byte result. The driver is external; inspect its version and trust it before running as root.

Supported CPU IDs: AuthenticAMD family 17h models 11h/18h (Raven/Picasso-class DDR4), family 19h model 61h (Raphael/Dragon Range DDR5). Other CPUs are rejected before any SMN operation. These are candidate maps, not hardware-verified compatibility claims. Only UMC 0/1 are probed; presence is checked via the pinned upstream channel-disable and chip-select bits, and the DRAM type is checked against the CPU map. LPDDR and other families are deliberately out of scope. A failed/unstable read fails the snapshot, not silently a zero. All-ones responses, implausible primary timings, and inconsistent register snapshots are rejected.

Read-only here means no mutation of UMC data or firmware settings. The driver sysfs protocol requires writing a four-byte address to select a read; eight-byte writes would mutate registers and are never issued. Its result is a global buffer, not a per-client transaction. The CLI serializes its own instances and rereads registers in reverse order, but this cannot establish atomicity with other clients or reliably detect every underlying driver error (the reference driver logs SMN read errors and can still acknowledge the request). Therefore this mode is experimental. There is no unsafe direct PCI fallback. See [driver protocol](https://github.com/amkillam/ryzen_smu/blob/main/README.md#syskernelryzen_smu_drvsmn) and [driver implementation](https://github.com/amkillam/ryzen_smu/blob/main/drv.c).

The maps are compiled directly from the checked-out submodule at commit 869b7e82572337e5a673e92230edc92bddf0e44b: [DDR4](https://github.com/irusanov/ZenStates-Core/blob/869b7e82572337e5a673e92230edc92bddf0e44b/Dictionaries/DDR4Dictionary.cs), [DDR5](https://github.com/irusanov/ZenStates-Core/blob/869b7e82572337e5a673e92230edc92bddf0e44b/Dictionaries/DDR5Dictionary.cs), and the refresh/ratio handling derives from Hardware/DRAM/Ddr4Timings.cs, Ddr5Timings.cs, BaseDramTimings.cs and MemoryConfig.cs at that revision. The CLI intentionally omits ambiguous rank-dependent refresh values, rather than selecting a first non-default value. All output clocks are nominal from the UMC ratio assuming 100 MHz BCLK; they are NOT measured frequencies. Optional Picasso and Dragon Range PM Table telemetry is described below. SPD and wider voltage telemetry remain future work.

Compare mode reports each populated UMC separately, never merges channel readings or treats unknown origins as Auto. The existing BIOS resolver controls whether saved settings are trusted. Running data is independent of UEFI access, and compare mode can return a running snapshot even when origins are unavailable; check origins_matched/origins_status. The comparison uses the existing DiffersFrom method, excludes nominal clocks, and does not assert AGESA application or a required reboot. JSON includes the selected raw UMC registers (not raw UEFI blobs) for reproducible diagnosis.

### APOB boot-time data (experimental)

    sudo ./zentimings --apob --json
    sudo ./zentimings --compare --extended --pm-table --modules --apob --json
    ./zentimings --apob-file apob.bin --json

APOB is the AGESA PSP Output Block left by firmware. It contains boot/training data, not live measurements. The Linux reader reuses the pinned upstream ApobEntry / ApobCoreMap enumerator, ApobMemGeneralConfig, ApobDimmSpdParser and EncodedValues/EncodedValueDictionaries without linking the Windows hardware drivers. The only portable Utils adapter supplies a bounded LE uint read. The DDR4 MEM group 1/type 2 decoder recognizes the upstream 256- and 496-byte entry layouts; populated channel slots can expose ProcODT, RTT, CAD drive strengths and setup delays, both original encoding and human-readable value. Unknown encodings remain N/A. Live DDR4 decoding is gated to the existing 17h CPU allowlist. Offline DDR4 layout selection is inferred from the entry size, not current host CPUID. The MEM group 1/type 17 parser can retrieve boot copies of DDR4 or DDR5 SPD even without a bound SPD EEPROM. Its limited SPD output uses the same CRC checks and field decoder as --modules. These results remain separate from live UMC and SMBIOS; no channel matching, no assertion that the firmware boot values are still active, no DDR5 termination layout in this PR.

Live acquisition is explicit opt-in and uses only the three addresses known by upstream Apob.cs (0x0A200000, 0x09F00000, 0x04000000). Before reading 16 header bytes and again before reading the complete declared table, the entire requested interval must be contained in an explicitly reserved or ACPI Non-volatile Storage resource in /proc/iomem, with no overlapping other resource (including System RAM or PCI/MMIO). Masked maps are rejected. /dev/mem is opened read-only; reads are bounded to 4 MiB, the header to 4096 bytes. No scan of physical RAM, arbitrary user-specified physical address, writes, mmap, kernel module, lockdown workaround or boot parameter changes. The kernel may deny even these reads (STRICT_DEVMEM, lockdown, permissions); report per-address diagnostics and stop. A second header read detects some concurrent changes, not an atomic snapshot. Offline mode accepts an exact complete binary table only and performs no hardware access; it does not require root. The parser rejects malformed lengths and overlapping entries, skips encrypted/duplicate target entries, and does not claim to verify firmware HMACs. Raw APOB and SPD bytes and serials are not emitted. Only share the normal parsed JSON, not raw physical-memory dumps.

Standalone mode returns 0 for a structurally parsed table (electrical/SPD fields may still be missing), 1 when unavailable; combined mode preserves valid UMC results on APOB acquisition failure. Check apob.available, diagnostics, electrical and spd independently. No change to the existing extended.electrical_status: the UMC backend itself does not acquire impedances. The synthetic tests check reserved range boundaries, masked maps, overlapping resources, System RAM exclusion, complete offline DDR4 config/SPD, encrypted entries, duplicate instances, and truncated/invalid input. M75n M33KT24A live test: standalone --apob --json returned unavailable. 0x0A200000 passed the resource policy but /dev/mem access was denied; 0x09F00000 was readable but lacked the APOB signature; 0x04000000 was skipped by the reserved/NVS policy. This validates the unavailable/diagnostic path, not live APOB decoding, and does not establish that APOB is absent. Further investigate kernel resource/access metadata and the firmware ACPI/WMI APCB Config path; do not change kernel security settings to obtain a successful result.

#### Offline SPI image discovery and extended DDR4 SPD

    ./zentimings --apob-image bios_afu.bin --json

Accepts an existing binary file up to 64 MiB, no root required. Searches for APOB signatures and accepts only a unique candidate with valid bounds, a complete contiguous chain of at least two known-group entries, matching upstream enumeration, and decoded memory evidence (recognized nonzero ProcODT or CRC-valid SPD). Multiple candidates are rejected rather than silently choosing a boot-data copy; use --apob-file on an extracted table instead. Image offsets are reported separately from physical addresses. No SPI hardware access, writes, firmware modifications or raw data exported. Data may be stale; this is not a live hardware snapshot.

Both kernel EEPROM and APOB SPD sources now project a privacy-filtered subset of the pinned upstream Ddr4SpdDecoder: manufacturer, DRAM maker, organization/capacity, ranks, bus/device widths, density, banks, rows/columns, package and thermal-sensor capability, JEDEC timing minima in ps, computed primary timings at maximum advertised rate, supported CAS values and XMP profile settings when present. No raw SPD, serials, manufacturing date or live PMIC/thermal data. Incomplete images or invalid module CRC omit XMP; base CRC failure still prevents decoding. XMP is decoded from its own stored data, not authenticated by base/module CRC; no claim of XMP being active. JEDEC rate uses rounded upstream clock (2667 rather than truncated 2666). DDR5 now also uses the pinned portable SPD/profile decoder, with explicit offline-only adapters for the report formatter's PMIC and privacy dependencies. No live PMIC hardware functionality is linked. Existing JSON fields remain; new nested ddr4 object is additive.

The source M33KT24A AFU dump was independently rechecked: SHA-256 matches the previous report; both SPD records are byte-identical after masking serial bytes. Regression embeds one such masked SPD in a synthetic legacy APOB chain and checks 4096 MiB, x16, one rank, DDR4-2667, both CRCs and no XMP; scanner tests false signatures, truncation, multiple valid candidates and no candidate. PR #16 hardware acceptance: the actual full-image CLI read succeeded on M75n, with the unique table at 0x002BA000, all expected entries and both valid SPD copies. On M75n (or a separate Linux host), run the command above on the existing dump; expected image_offset 0x002BA000, 20 entries, two SPD copies, ProcODT 60 ohm. No new AFU acquisition required.

#### Legacy Picasso S3 replay observations (experimental)

The same offline commands (and a successfully acquired compatible live APOB boot copy) expose an additive `apob.replay` object for the narrowly fingerprinted M33KT24A v0x13 layout. It is null on other or invalid layouts; this is not an S3 executor or a general register dump. The 48-byte APOB entry header is excluded from all payload offsets. In GEN 7/4 (13904 bytes including entry header), a 32-byte stream header has count 1454 at +0x10. Records are 8-byte LE pairs starting at +0x20; the exclusive end is +0x2D90, with 2192 opaque bytes after it. The earlier +0x28 start was off by one record. This intentionally overfits one proven format rather than extrapolating to other boot/firmware versions.

Report only the shared allowlist of known UMC addresses; last observed word and complete ordered history (payload offsets) are candidates, not a proof of executed writes or present hardware. No arbitrary-address reads, register writes, physical-memory scanning, raw replay payload or opaque data export. The two observed address blocks are indexed 0 and 1; do not associate them automatically with SPD or electrical slots. Marker counts and companion record boundaries are structural metadata, not interpreted opcodes. No HMAC validation.

### Memory module inventory and optional SPD acquisition

    sudo ./zentimings --modules
    sudo ./zentimings --modules --json
    sudo ./zentimings --compare --extended --pm-table --modules --json

Explicit opt-in. Reads the kernel-provided binary SMBIOS table /sys/firmware/dmi/tables/DMI directly (no dmidecode dependency). Type 17 records with populated or unknown capacity are listed, including locator, bank locator, manufacturer, part number, memory type, form factor, capacity, ranks, widths, rated/configured data rate and configured voltage when present. Empty slots are skipped; unknown fields remain null. These are firmware-reported values, not live measurements. A malformed table produces an inventory status rather than invalidating a good UMC snapshot.

The same mode checks already-enumerated I2C device directories at SPD addresses 0x50–0x57 and reads eeprom only for devices bound to ee1004 or spd5118. No I2C address scans, direct SMBus accesses, driver loading/binding, or sysfs writes. SPD reads may involve kernel-managed bus transactions. A missing EEPROM is reported explicitly. The initial SPD decoder checks DDR4/DDR5 device type, bounds and base CRC (DDR4 bytes 0–125, DDR5 bytes 0–509), also DDR4 module CRC when present. Exports a limited set of revision, module part number, manufacturer JEP106 code and tCK minimum/rate derived from tCK; the manufacturing area is not covered by the base CRC. The calculated rate is not a measured clock or rounded JEDEC speed grade. This is intentionally **not** full SPD/profile decoding: capacity/organization, all JEDEC timings, XMP/EXPO, and PMIC/temperature remain follow-up work. No raw SPD, serial numbers or asset tags are emitted. No automatic association between SPD device, SMBIOS locator and UMC channel is assumed.

On M75n no bound SPD device is expected based on the previous hardware report; SMBIOS should show two Micron 4 GiB single-rank DDR4 modules rated 2667 MT/s, configured 2400 MT/s, 1200 mV. Standalone --modules does not require SMN or UEFI variable access; it returns 0 if module inventory or valid SPD is available, otherwise 1. In combined mode, check the separate inventory statuses; optional inventory failure does not discard a working UMC result. The --sysfs-root option is permitted for standalone fixture testing only; never point it at untrusted directories with sudo. Synthetic tests cover two populated modules plus an empty slot, privacy exclusions, valid DDR4/DDR5 SPD CRC, invalid/truncated SPD and malformed SMBIOS. Hardware acceptance on M75n M33KT24A: combined --compare --extended --pm-table --modules --json and standalone --modules succeeded. SMBIOS reports two Micron Technology 4ATF51264HZ-2G6E1, 4096 MiB each, one rank, 64-bit data/total widths, DDR4 SODIMM, rated 2667 MT/s, configured 2400 MT/s and 1200 mV, bank locators P0 CHANNEL A/B. SPD correctly reports no bound devices. Positive SPD acquisition still requires another machine.

### Offline AMD BIOS directory provenance

`--apob-image` additionally reports `bios_directory`: checksummed $BHD/$BL2 tables with type 0x61 (APOB RAM destination) or 0x63 (NV region). Fletcher32 is calculated over the count, reserved word and bounded 24-byte entries; the checksum is not cryptographic authentication. Mode 0 resolves a physical address in a standard 8/16/32/64 MiB full-image top-of-4-GiB mapping; mode 1 is a flash offset; modes 2/3 are intentionally unresolved. Duplicate directory references are grouped by offset and size. Matching means the validated APOB begins at the advertised region start and fits entirely within it. The directory scan is bounded to 4096 cookie candidates and 256 entries per table. Metadata is still reported if no valid APOB exists (exit 1 unchanged). This does not choose an active directory or resolve ambiguous tables, change the signature/CRC acceptance policy, or permit new live reads. Standalone and live APOB results leave this field null.

References: [coreboot PSP integration](https://doc.coreboot.org/soc/amd/psp_integration.html), [amdfwtool Fletcher32](https://chromium.googlesource.com/chromiumos/third_party/coreboot/+/f44356712ac23e55e461db5209ddc5b59e381978/util/amdfwtool/amdfwtool.c).

